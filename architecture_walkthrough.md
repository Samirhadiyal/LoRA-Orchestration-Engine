# NeuroMesh — AI Knowledge OS: Architecture & Engineering Walkthrough

This document provides a comprehensive architectural walkthrough of the NeuroMesh repository (`LoRA-Orchestration-Engine`), covering the completion of **Phases 1 through 5 (Tracks A & B)**. It serves as a reference guide for the core execution pipeline, domain-specific tracks, testing infrastructure, and future roadmap.

---

## 1. System Overview & The Core Execution Pipeline

The core of NeuroMesh relies on a deterministic, state-driven orchestration pipeline powered by LangGraph. This ensures that the AI's complex reasoning and execution are fully observable, resumable, and robust against infinite loops.
### The LiFecycle of a User Query

The execution pipeline follows a strict unidirectional flow:

1. **USER**: Submits a natural language query via the API.
2. **PLANNER**: A lightweight LLM call decomposes the user query into a structured JSON `ExecutionPlan`.
3. **STATE (`ExecutionState`)**: The plan is loaded into a strongly-typed LangGraph state object, initializing an array of `ExecutionStep` objects.
4. **LANGGRAPH ROUTER (`app/router/graph.py`)**: The compiled state graph takes over, routing the current step.
5. **HANDLERS (`app/router/handlers.py`)**: The registry maps the step's requested action to a concrete execution handler.
6. **CONTEXT OPTIMIZER (`app/context/optimizer.py`)**: Aggregates and semantically compresses retrieved data and tool outputs.
7. **LLM GENERATION**: The optimized context and query are passed to the selected LoRA adapter or base model.
8. **RESULT**: The final synthesized answer is streamed or returned to the user.

### State Management and Loop Prevention

The `ExecutionState` and `StepStatus` enums tightly control the flow:

| Status | Description |
| :--- | :--- |
| `PENDING` | The step is queued but hasn't started. |
| `IN_PROGRESS` | The step is currently being executed by a handler. |
| `RUNNING` | (Internal to graph) The graph node is actively processing this step. |
| `COMPLETED` | The handler finished successfully; `current_step_index` advances. |
| `FAILED` | The handler encountered an error; the graph halts to prevent runaway loops. |

**Preventing Infinite Loops**: `app/router/graph.py` uses `current_step_index` to linearly iterate through the predefined steps. The conditional edge (`check_next_action`) only loops back if `current_step_index < len(state.steps)` and `status != ExecutionStatus.FAILED`. This mathematically guarantees the graph will terminate, unlike naive autonomous agents.

### Handler Protocol and Registry

`app/router/handlers.py` defines a strict `RouteHandler` protocol:
```python
class RouteHandler(Protocol):
    async def execute(self, state: ExecutionState, step: ExecutionStep) -> ExecutionState: ...
```

`app/router/registry.py` acts as the dependency injection container, mapping planner actions to handler singletons:
*   `"rag_search"` ➡️ `RetrievalHandler()`
*   `"sql_query"` ➡️ `ToolHandler()`
*   `"lora_adapter"` ➡️ `ExpertHandler()`
*   `"direct_llm"` ➡️ `GenerationHandler()`

## 2. Track A: External Tools, API & Streaming Architecture (Systems Domain)

Track A focuses on integrating external knowledge and maintaining high-performance API boundaries.

### Safe SQL Execution (`app/tools/sql_agent.py`)

The `SQLAgent` bridges natural language and structured databases using a two-step process:
1.  **Translation**: An LLM is prompted strictly to output a read-only PostgreSQL query as a JSON object.
2.  **Execution Guardrails**: Before execution via SQLModel/SQLAlchemy, the query string is rigorously checked (`cleaned_sql.startswith("SELECT") or cleaned_sql.startswith("WITH")`). If it passes, it executes against the `chat_sessions` schema, returning the row count and raw data.

### MCP Client (`app/tools/mcp_client.py`)

The `MCPClient` standardizes how NeuroMesh talks to the outside world (web searches, weather APIs, calculators). It catches boundary errors (`ConnectionError`, `TimeoutError`) and normalizes the payload into a standard `dict` format, ensuring the orchestrator never crashes due to a flaky external API.

### Asynchronous Streaming & Persistence

*   **Streaming (`app/api/stream.py`)**: Uses FastAPI's `StreamingResponse` to push Server-Sent Events (SSE). It yields tokens as they are generated by the LLM, keeping the event loop unblocked via `asyncio`.
*   **Checkpointing (`app/router/persistence.py`)**: LangGraph checkpoints the `ExecutionState` at each node transition. This allows long-running tool calls (e.g., a slow web scrape) to be suspended and resumed, making the system highly resilient to transient failures.

## 3. Track B: Neural Networks, Hybrid RAG & Context Optimization (ML Domain)

Track B manages the heavy lifting of AI models, vector search, and VRAM optimization.

### Vector Database & Hybrid RAG (`app/retrieval/`)

The retrieval pipeline uses a sophisticated hybrid approach:
*   **Dense Search**: Uses `BAAI/bge-small-en-v1.5` embeddings (384-dimensional cosine distance) stored in the Qdrant `neuromesh_knowledge` collection.
*   **Sparse Search**: Uses BM25 for precise keyword matching.
*   **Fusion & Reranking**: `app/retrieval/search.py` combines dense and sparse hits using Reciprocal Rank Fusion (RRF), then reranks the top candidates using the `cross-encoder/ms-marco-MiniLM-L-6-v2` model to maximize relevance.

### Semantic Context Optimizer V2 (`app/context/optimizer.py`)

LLMs have finite context windows. The optimizer ensures we never exceed them while preserving the highest-signal information:
1.  **Budgeting**: Enforces a strict 12,000 character limit.
2.  **Prioritization**: `tool_results` (like SQL output) are formatted first and given absolute priority over fuzzy RAG context.
3.  **CPU-Bound Deduplication**: To keep GPU VRAM free for LLM generation, the optimizer runs on the CPU. It uses `TfidfVectorizer` and `cosine_similarity`. Any RAG chunks with a similarity `> 0.82` to an already-included chunk are discarded.

### LoRA Adapter Management (`app/llm/lora_manager.py`)

Running multiple specialized experts on a laptop GPU (RTX 3050, 4GB-6GB VRAM) requires aggressive memory management:
*   **4-bit QLoRA**: The base model (e.g., Mistral-7B) is loaded using `BitsAndBytesConfig` in NF4 precision.
*   **LRU Caching**: `_active_adapter_id` tracks the currently loaded LoRA. If the next step requests the same expert, the disk read is short-circuited.
*   **VRAM Flushing**: Before swapping adapters, `unload_all()` explicitly calls `del self.model`, `gc.collect()`, `torch.cuda.empty_cache()`, and `torch.cuda.ipc_collect()`. This guarantees the VRAM is cleared, preventing Out-Of-Memory (OOM) crashes during the swap.

## 4. Testing, Quality & Evaluation Suite

A robust CI/CD and evaluation pipeline ensures NeuroMesh remains stable as complexity grows.

### Router & Regression Tests (`tests/router/`)

The suite includes 8 core regression tests that validate graph determinism. These tests ensure that the `ExecutionState` transitions correctly through the `check_next_action` conditional edges and that handlers accurately map planner outputs to state mutations without side effects.

### Phase 5 Evaluation Suite (`tests/evals/`)

We evaluate the ML components using the **Ragas** framework:
*   `test_ragas_metrics.py`: Evaluates the RAG pipeline on three critical axes:
    *   **Context Precision**: Did the reranker put the most relevant chunks at the top?
    *   **Context Recall**: Did we retrieve all the information needed to answer the query?
    *   **Faithfulness**: Is the final LLM response grounded *only* in the retrieved context (no hallucinations)?
*   **Offline Fallbacks**: `conftest.py` implements mocking shims for Qdrant and LLM endpoints. This ensures that CI builds and trajectory tests (`test_trajectory.py`) run reliably even without network access or active GPUs.

### Code Quality Standards

The codebase adheres strictly to modern Python standards:
*   **Ruff**: Enforced linting and formatting.
*   **Exception Handling**: Zero bare `Exception` catches (`BLE001`). All exceptions are explicitly typed tuples (e.g., `(RuntimeError, OSError)`) mapping to specific failure domains (network, disk, tensor allocation).

## 5. Roadmap: What Remains (Phase 6+)

With Phase 1-5 complete, the orchestration engine is stable, stateful, and hardware-optimized. 

### Phase 6: Multi-Agent Swarm Collaboration & Edge Device Deployment

The next architectural evolution will shift NeuroMesh from a single-node orchestrator to a distributed swarm:
1.  **Swarm Orchestration**: The LangGraph router will be upgraded to support parallel edge execution, where the `ExpertHandler` can delegate tasks to independent agent nodes running on different physical devices.
2.  **Edge Device Deployment**: Compiling the execution graph and LoRA manager for lightweight edge environments (e.g., Apple Silicon, ONNX Runtime). 
3.  **Cross-Agent State Sync**: Upgrading `app/router/persistence.py` to use a distributed Redis/Postgres state store, allowing agents to hand off `ExecutionState` seamlessly across the network.
